What is a GitHub Codespace? (1-paragraph version)

A Codespace is a Linux computer that runs in GitHub's cloud, with VS Code (a code editor) opened in your web browser. Nothing installs on your laptop — everything happens on the cloud machine. You write code in the browser, save it to GitHub, and it's still there when you close the tab. Free each month — 120 core-hours (about 60 hours of use on the standard 2-core machine) on a personal account, or 180 core-hours (~90 hours) once you verify as a student — then it pauses until the next month. Like Google Docs, but for a programming environment.

Important — when you're done, stop your codespace. Idle codespaces keep using your monthly hours until they auto-suspend (default: 30 min). To stop one immediately: visit github.com/codespaces and click ⋯ → Stop codespace. Leaving a tab open all day will eat through your free tier in under a week.

Storage counts too. Even a stopped codespace keeps using your free storage (15 GB) — GitHub only stops counting when you delete it (⋯ → Delete). A large dataset can hit the storage limit before your hours run out, so delete codespaces you've finished with.

Your first 30 minutes

The shortest path from a blank browser to something real. By the end you'll open one example evidence capsule, change a single number, and watch every estimate, chart and self-audit check update — the fastest way to feel what a self-checking research tool does, and proof the whole thing works.

1. Open your workspace. Click Start in GitHub Codespaces at the top and wait ~2–3 minutes while it builds. A code editor opens in your browser with everything already set up — nothing to install.
2. See it work — open one capsule. Open the living evidence capsules, pick one (say a meta-analysis), change one number in its data, and watch the result, chart and self-audit checks re-run instantly. That's your first success. Each capsule is a single offline page that runs its own statistics and checks itself before asking you to trust it — the quality bar made tangible.
3. Add your free AI key and run a test prompt. In a Codespace the AI agent is already installed — you just add a free key (see Set up your AI key), then ask it: gemini "Summarise the rules in my .claude/rules/ folder". If it answers with the E156, lessons, advanced-stats and rules content, your agent is wired up.
4. Learn the method. The real value is a way of working: brainstorm → spec-lock → plan-lock → TDD → audit. Read STUDENT-WORKFLOW.md for the 5-step path to your first paper, the case studies behind each step, and what UNVERIFIED means (it is not a release pass). Worked-example repos to clone and reproduce: ma-workbench (sglt2i-hfpef), repro-floor-atlas, responder-floor-atlas, impossible-ma.
5. Create your first E156 project. Scaffold a new project with the student new CLI (from e156-student-starter) and aim for one small, reproducible output: one repo + one dashboard + one 156-word micro-paper. Pick a starting point from What you can build below.

Once your workspace is open, you can build small but real research artifacts in a few hours. Pick one. Each is sized for a single sitting and produces something you can put on your CV.

Install on your own machine

Using Codespaces? You can skip this whole section. Everything below is only for installing on your own laptop instead of in the browser. The cloud workspace already has Python, R, and Node set up for you.
Is this safe? Yes — it's open source, and you can read every script before running it. The safest route is GitHub Codespaces: nothing installs on your laptop at all. If you do install locally, the recommended path below is to clone the repo and read the scripts first, rather than pipe a web address straight into your shell. For institutional or shared machines, use the tagged git clone route with the signed release (see Security model) instead of the one-liner.

Step 1 — prerequisites (local install only)

On your own machine, install Python and Node.js first (both free). R is optional — you only need it for the R cross-validation check, and the installer just prints a warning and carries on if R is missing. The installer does stop with a clear message if Python or Node is absent. A 156-word first paper does not need R.

Python 3.11 or newer (required)

Critical: Windows 10/11 ships with a Microsoft Store stub at python.exe that looks like Python is installed but actually opens the Store when you try to use it. You must install real Python from python.org, not the Store. The installer detects the stub and refuses to continue if it's all you have.
1. Download from python.org/downloads (latest 3.x).
2. Run the installer. On the first screen, tick "Add python.exe to PATH" — this is the most-missed step.
3. Click Install Now. It takes about 1 minute.
4. Verify in a new PowerShell window: 
python --version
You should see a Python 3.x version. If you see "Python was not found" or it opens the Microsoft Store, the Store stub is shadowing your install — see Advanced for the one-line fix (turning off the app-execution alias).

Node.js 20 or newer (required)

Needed because Gemini CLI / Claude Code / Codex are all distributed via npm.

1. Download the LTS version from nodejs.org/en/download and run it (default options).
2. Verify in a new PowerShell window: 
node --version
npm --version
You should see v20.x.x or higher.
R 4.5+ (optional — only for the metafor cross-check)

R is used to cross-validate your meta-analysis pools against the gold-standard metafor package. It is entirely optional — skip it and the installer simply prints a warning and moves on; your dashboards still work, they just won't run the extra R cross-check. Add it later if you want that belt-and-braces validation.

1. Download from cran.r-project.org/bin/windows/base/ and run the installer (defaults are fine).
2. Add R to PATH and install metafor — the terminal steps are in Advanced, since they involve editing PATH by hand.

Step 2 — install (clone, read, run)

Recommended — download the installer, read it, then run it. You're about to run a script that writes files into your home folder, so the safest habit (especially if you've never used a terminal) is to get the source first, look at it, and run it from disk — not pipe a web address straight into your shell.

git clone https://github.com/mahmood726-cyber/e156-ecosystem-starter
cd e156-ecosystem-starter
# open and skim install/install.ps1 (Windows) or install/install.sh (macOS/Linux/WSL)
# — both are short and commented — then run the one for your system:
.\install\install.ps1        # Windows PowerShell
bash install/install.sh      # macOS / Linux / WSL

The installer asks a few Yes/No questions (all default to Yes) and finishes in about 2 minutes. Confirm it worked by listing the installed rules: ls ~/.claude/rules (macOS/Linux) or ls $env:USERPROFILE\.claude\rules (Windows) — you should see four .md files (e156, lessons, advanced-stats, rules).

Prefer a one-click download instead? Grab the installer file and run it:

Download .bat (Windows) Download .sh (macOS / Linux)

On Windows the .bat may be blocked by Smart App Control — see Advanced for the fix. On macOS/Linux: chmod +x e156-setup.sh && ./e156-setup.sh.

One-liner install (faster, but pipes a remote script into your shell)

If you understand the trade-off — you're running code straight from the web before reading it — the one-liners are:

irm https://mahmood726-cyber.github.io/e156-ecosystem-starter/bootstrap.ps1 | iex   # Windows PowerShell
curl -fsSL https://mahmood726-cyber.github.io/e156-ecosystem-starter/e156-setup.sh | bash   # macOS / Linux / WSL

The clone-and-read path above is preferred, especially for a first-time terminal user. The source is open and auditable: bootstrap.ps1, install.sh.

Set up your AI key (agent CLI)

The starter rules and memory are designed for three agents. You only need one to get going. If you're starting from zero, install Gemini CLI — the free tier is the most generous.

In a Codespace, Gemini CLI is already installed for you. You can skip straight to step 3 below — getting your free API key — and set it with export GEMINI_API_KEY="your-key" in the terminal.

Option A: Gemini CLI (recommended — free tier)

1. Install Node.js 20 or newer (Windows installer, default options).
2. Open a fresh PowerShell window and install the CLI globally: 
npm install -g @google/gemini-cli
3. Get a free Google API key (no credit card needed):
  1. Go to aistudio.google.com/app/apikey and sign in with any Google account.
  2. Click Create API key → Create API key in new project.
  3. Copy the long key (starts with AIza...). Treat it like a password — never paste it into a public repo or chat.
4. Tell Windows the key is yours so the CLI can find it: 
setx GEMINI_API_KEY "paste-your-key-here"
Close and reopen your terminal so the new variable loads.
5. Test it: 
gemini "summarise this file" < README.md
If you get a coherent answer, you're done.
Free-tier limits (Google AI Studio): the free tier needs no credit card, and Gemini Flash is usually enough for small research tasks. The exact limits change by model and by account, so check your active limits in Google AI Studio (or the rate-limits page). If you hit a wall, the CLI tells you when the quota resets.

What this toolkit cannot do

Every tool here states its blind spot next to its feature, because a tool that hides its blind spot is the thing this project exists to replace. Read this section before you trust a number it gives you.

  • One-registry checks over-report hiddenness. Any check built on ClinicalTrials.gov alone cannot see PACTR, ISRCTN, CTRI, or ChiCTR registrations. It will falsely flag African- and Asian-registered trials as missing. See Project 4 above.
  • Cross-family agreement is weaker than it looks. A panel of models drawn from different families gives roughly two effective independent votes, not one per model. Do not read panel agreement as replication.
  • Our nulls, published: seven novelty claims we tested did not survive; six forensic bids returned clean nulls. These are findings, not embarrassments — they are here so you do not spend your time re-running them.
  • Coverage floors are usually our failure, not the world's. When this toolkit reports "no data available", treat that as a statement about the toolkit's reach until you have checked a second source yourself.
  • The self-audit's CLEAN means "no detector fired", not "correct". Its 16 checks are text-pattern matching over one rendered page — they do not understand your clinical question, cannot see your extraction sheet, your protocol or your actual search, and cannot tell a well-justified decision from a badly-justified one, only whether a justification is present. Nothing in it recomputes your pooled estimate from your raw data. The classes it cannot catch are listed by name in the error library, and they include the worst one on the list: a number that is simply wrong at the source, inside a table that is internally consistent.
  • The double-count check is bounded, and matches exactly. It searches subsets of 2–5 rows in tables up to 60 rows; anything larger returns INCONCLUSIVE, which is honest but is not a check. And it finds sums that match to the patient — a duplicate where one report dropped two patients for missing data will not match, and will not be found.
  • The contamination list is a list. The template-leak detector knows the donor strings from our corpus. Your template will leak different words and it will not know them. Two of its rules exist only because running it on real files produced false positives ("Conflicts of interest: None declared" is correct English; NaN inside a <script> is ordinary JavaScript). Expect more.
  • The forest-plot order check cannot see a picture. It compares the label and value arrays, and the plot order against the extraction table. A forest plot drawn into a <canvas>, rendered server-side, or pasted in as an image is reported not applicable — which is honest, and is not a check. It also cannot tell you the order is wrong if labels and values were mis-paired back at extraction and have been consistently mis-paired ever since; it only sees two views of one file disagreeing.
  • The registry-ID check is offline, so it cannot confirm an ID is the right one. It knows that an NCT number is well formed, that the page does not contradict itself about which trial an ID belongs to, and that an ID is not older than its own number block. A perfectly well-formed NCT that belongs to a different trial passes clean. Confirming an identifier points at the study you actually analysed means opening the registry record yourself — and a wrong-but-well-formed ID is worse than a missing one, because it sends your reader to a real trial page and so makes your provenance look stronger than it is.
  • Quiet on our corpus is not the same as sensitive. Those two detectors fired on none of 431 real dashboards. That measures how rarely they cry wolf on already-repaired files. It is not evidence of how much they would catch in yours; that rests on the known-bad fixtures in the test suite, where each detector must fire on a defect and stay silent on a correct page.
  • The optional pooling witness has a known false FAIL. Its scale-invariance relation doubles every effect without rescaling the variances, which is not a change of units — so a correct random-effects estimator fails it by construction (measured ratio 1.862, not 2.000, because τ² absorbs the spread). The relation is valid for fixed-effect pooling only. The audit names this rather than hiding it.
  • The adversarial cross-family gating is not in the free-tier kit. The model-dependent half of this work — running a finding past independent model families to see whether it survives — needs paid API access and cannot run offline. It is documented as optional guidance, not shipped as a capability, and its own limit is the one stated above: a multi-family panel gives roughly two effective independent votes, not one per model. What you get for free is the deterministic half, which is the half that does not need a model at all.

Prior art — we are mostly not first

Assume this project is last until shown otherwise. Named, so you can go read the originals and judge for yourself:

  • Weak supervision / labelling rules — Snorkel and the data-programming literature. Our Tier-1 rules are this idea, applied to evidence synthesis.
  • Model cascades for cost — FrugalGPT. Our cheap-check-first routing is this idea.
  • Document-processing harnesses — ScriptoriumWS / Alfred.
  • Estimating what you missed — capture–recapture methods, long-standing in software engineering and ecology before we applied them here.
  • Registry-vs-publication discrepancy — Hartung & Zarin (2014); Wieseler (2013) on regulatory data completeness. They found it first.
  • Missing-data handling in synthesis — Mavridis (2020).

What is ours: the assembly — offline-first, open-data-only, fail-closed, runnable on a weak laptop with no API key and no paywalled source. Not the parts.

Technical reference & security

The plain-language intro at the top calls this "AI rules, quality checks, and project memory." Here are the real component names, what each does, and the security model — for supervisors, IT staff, and the curious.

What's new in the toolkit

The starter keeps moving. If you installed an earlier version, here's what has been added since — all of it still offline-first and gentle on a free-tier quota, because that's the constraint most students are working under.

Spend fewer tokens — reuse what the kit already ships

Three small offline helpers (no internet, no AI, no cost) cut the biggest hidden drain on your free requests: asking an agent to re-write something the ecosystem already contains. reuse.py finds an existing function to copy, recall.py pulls only the saved notes relevant to your question instead of loading your whole memory file, and find-related-repos.py checks whether you've built something similar before. See the token-budget guide for where your free requests actually go.

Turn a trial into an analysis config — now across 17 fields

The RCT extractor now auto-detects 17 disease areas, including many that matter most where this toolkit is used — HIV, malaria, typhoid, schistosomiasis, sickle cell, cholera, TB, maternal/neonatal care, and more. Paste an abstract, get a starter meta-analysis config. The student path is standard-library-only (no heavy installs); the large PDF/science dependencies stay optional. Source: rct-extractor-v2.

Rebuild the whole meta-analysis toolkit — offline

Five optional layers now let you recreate the full workflow end-to-end without spending tokens, each with a zero-cost path you can just open and read:

  • Dashboard kit — turns a small JSON config into a self-contained meta-analysis dashboard (standard-library only, offline).
  • AACT cockpit & AACT kit — analyse ClinicalTrials.gov / AACT data on your own machine, or just read the worked examples.
  • Pairwise70 workbench — a static gallery that reproduces each analysis in your browser, no Python needed.
  • E156 capsule + chart-kit — the 7-sentence paper contract plus a ~120-line pure-SVG forest-plot kit and a pre-baked sample. The lowest-footprint layer in the ecosystem.

These sit alongside the 40 living evidence capsules already on this page.

A verifier that checks your meta-analysis math

The Overmind verifier is now at a stable v1.0.0 release (pinned to a signed tag) and has gained an evidence-synthesis subsystem: a deterministic pooling engine and a gold-benchmark that reproduces a published pooled estimate and fails closed if the numbers don't match, plus screening-recall calibration, claim-grounding, and PRISMA-flow checks. Same idea as the capsules — don't trust a number until it has checked itself. Source: overmind.

Method and standards you can map your own work to

The rules that guide the agent picked up new method guidance too — for example, requiring a held-out test split before any “we tuned or optimised it” claim, and a just-in-time rule index so the agent loads only the rules it needs for the task in front of it. The method also encourages an open-data-only, provenance-verified way of correcting published results: rebuild a number from freely-available sources (PubMed, ClinicalTrials.gov, Europe PMC), and where it doesn't hold up, add a corrected value beside the original with a link back to its source — never overwrite. These checks are written to follow and cite recognised standards — the Cochrane Handbook, Chapter 6 (the right effect measure for the kind of data), GRADE indirectness, and the transitivity assumption — and the whole ecosystem is mapped to the 2025 RAISE framework for responsible AI in evidence synthesis, so you can see — and learn — where your own project meets the bar.

A library of real meta-analysis errors — and a self-audit that looks for them

A new optional layer, and the most directly useful one if you are writing a review rather than building tools. It has two halves.

The meta-analysis error library catalogues ways a meta-analysis goes wrong — each class with a plain-language description, a real worked example with real numbers, why it slips past a careful reader, and how to detect and correct it. Every class was found in an actual review or an actual generated dashboard; none were invented to round out a list. The most surprising finding is worth stating up front: across 626 generated review dashboards audited and repaired one file at a time, the three near-universal defects were not statistical. They were a pooling engine that would combine things that do not belong together (610 of 626, 97%), a provenance claim the page was not entitled to make — a commit timestamp offered as prospective registration (540, 86%) — and a status badge that was green because someone wrote it green (532, 85%). The arithmetic was almost always right; the framing around it almost never was.

Those counts are a point-in-time snapshot (2026-08-02) of one corpus from one generator — dashboards with a shared ancestor, which is exactly why three defects reach 85%. Read them as “this is what a family of generated reviews gets wrong”, not as a field-wide rate.

The second half is machinery, not advice. scripts/meta-self-audit.py points 18 deterministic detectors at your own single-file dashboard — offline, standard-library-only, no API key, no AI call, about a second on a weak laptop. It looks for a continuous outcome reported as a ratio, an effect measure that contradicts the extracted data, the same trial counted twice (a subset-sum over the participant column — the check that catches a pooled trial entered alongside its own component arms), a point estimate printed outside its own interval, Egger's test run below k=10, a PRISMA flow that does not add up, “fragility index = 0, therefore robust”, a missing harms synthesis, template text describing the wrong drug, a commit timestamp claimed as PROSPERO registration, and more. Each finding comes with the evidence and the correction, not just a flag.

Two detectors were added after the first release, both for defects the corpus run had catalogued but not yet automated. Forest-plot rows labelled in a different order from their values — the pooled diamond stays correct, because the summary row never reads the labels, so the only way to catch it by eye is to check an individual trial against its source. And a registry identifier that cannot be right: a malformed NCT number, or the same ID attached to two different trials, or an ID stated against a year before that block of numbers existed. Both check the file's own internal consistency; neither needs the network.

Worth knowing how those two were tuned, because it is the honest part. Both were run across 431 real dashboards, and three separate rounds of false positives were traced to root cause and removed — a proximity rule that bound one trial ID to the nearest capitalised word and so fired on 38 of 40 files; a sample size of 1,912 read as a publication year; and one trial name split in two because it appeared once escaped and once decoded. None of those were caught by the unit tests. A test suite written by whoever wrote the detector shares its blind spots; only real files find that class of bug.

It is fail-closed by construction: there is deliberately no verdict called “passed”. A check that cannot establish the facts it needs returns INCONCLUSIVE and exits non-zero, because “I could not check this” quietly becoming “this is fine” is itself one of the catalogued errors — and a tool that committed it while detecting it would not deserve to be believed. If you have Overmind installed it can additionally reuse Overmind's metamorphic witness to test your pooling code against invariants any correct implementation must satisfy. The detectors' own blind spots are listed above under what this toolkit cannot do, and in more detail in the library.

Five classes added 2026-08-19 — and five errors of ours

The library gained five classes, and the day that produced them produced a result worth leading with. Auditing a working corpus of 135 topic objects, the stored numbers held: six pooled figures survived independent recomputation, six recorded limitations survived independent test, and 0 of 47 search records were found resting on a completeness proof that does not hold. Every substantive correction was to a reason, an attribution, or a check — never to a stored quantity. The reviews kept being right and the instruments kept being wrong.

Four of the five new classes are defects in our own published surfaces, and they are written up in the same tables, at the same size, as everyone else's. A dashboard of ours was serving 92 pooled estimates the reviews themselves had withdrawn — of 109 rows that could be checked at all, with 602 more uncheckable, so 92 is a floor. Five of 522 index cards were serving an external benchmark in the slot where the review's own result goes, three of them live and previously unknown; the worst served a confident RR 0.07 (0.01–0.32) for a review that had withdrawn its estimate entirely, so the review said it could not answer while the index said it answered decisively. Summing trial counts across our own reviews double-counted 68 of 354 trials (19.2%), against 286 distinct registrations — after merging nine clusters that turned out to ask one question, 53 of 339, with the distinct count unmoved at 286, which is the check that the merge removed double counting and no evidence.

The fourth is the one we would least like to publish. A check we wrote to verify an outside model seat's report of the dashboard problem returned zero — because it looked up pooled_or and the field is pooled_OR. Every row was skipped and the empty tally read exactly like a clean corpus. An outside seat handed over a true finding and our own check said it was false, and had that zero been believed the finding would have been filed as "the other seat was wrong". It is open, with no detector, and it reproduced twice more the same day in the selftests of instruments written after it was written down. And a claim from our own reporting — "37 of 144 topics carry a templated question" — was withdrawn the same day for a bad denominator; the measured replacement is 80 of 135 live topics that state a question at all.

That failure mode has its own page: proving a detector can fail — four forms of a check that reports clean because it never looked, the delivery check that fetched the build directory from itself and so passed for 96 commits while the pages a reader opens were stale, and the four remedies that are mechanical rather than a matter of remembering. It ships with a runnable check, python scripts/gate-can-fail.py --selftest: a file named a gate must contain a reachable failing exit, because a gate that cannot fail is a trap for whoever wires it in next. Measured on the corpus that motivated it, 39 of 39 files named a gate can now fail; the sweep found four that could not, and all four turned out to be correctly-built advisory tools wearing the wrong name — they were renamed, not made to block, which is the difference between an error and a defensible different choice.

One corpus, 135 topic objects, audited by its own maintainers on 2026-08-19, and enriched by construction — a corpus under active repair, whose instruments were under deliberate scrutiny that day. These are counts in one corpus, not rates for anything. Three of the five new classes have no detector — they were found by hand or by a one-off sweep, and they are published anyway, because a class you can name and cannot yet catch is worth more to a reader than a silence. The other two ship a standalone check each (below). meta-self-audit.py looks for none of the five, so a CLEAN from it says nothing about any of them.

The two that do have one. Proving a search finished is the runnable half of the pagination class: python scripts/search-record-reconcile.py --selftest asserts 10 of 10, including that the real failing record — 203 returned against a reported 430 — is refused and names the shortfall of 227, and that the honest record beside it, 137 against 137 with an equally empty cursor, does not fire. A check that cannot stay quiet is not a check either. Two real records ship with it, one of each kind. The same page carries the recall measured beside those searches — 3 of 3, 2 of 4, 3 of 4 against three reviews' own included sets — and every miss turned out to be worth more than the score: one was a mechanical heart valve trial a venous-thromboembolism filter was right to exclude, which is a question about the review and not about the search. Two of the trials in another review are registered on a national registry rather than ClinicalTrials.gov, so that search cannot surface them at any recall — a recall figure is against a database, not against the literature.

And python scripts/pooled-point-achievable.py --selftest asks whether a served headline is reachable at all from the trials a forest plot shows. It does not search estimators — an enumeration that finds nothing proves nothing about the estimator it did not try — it bounds them: every fixed weighting is a convex combination of the per-trial effects, and inside that hull the random-effects family runs from the fixed-effect weights to equal weights and nowhere else. On its worked case the hull does not convict and the narrower bound does, and the output always says which limb it used. Its own limit is on the tin: it bounds arithmetic, not provenance — a reachable number can still have come from somewhere else entirely, which is exactly what that case turned out to be.

Where to get the number — a sourcing method you can follow

The library tells you what is wrong; the new sourcing method tells you where to get the number that puts it right, using only free sources. It sets out the hierarchy in yield order — supplementary tables of prior published meta-analyses first (the richest source, and the one most often skipped), then open-access primaries via PMC and Europe PMC, then FDA statistical reviews and EMA EPARs, then ClinicalTrials.gov posted results. No subscription, no institutional login, no API key.

Three rules do most of the work. Every number carries a provenance line naming which table it came from, written at the moment you change it. Corrected values go beside the original, never over it, with a source link — overwriting destroys the only evidence that a correction happened and leaves your reader unable to tell a transcription fix from a silent re-analysis. And if you cannot source a number, you leave the original standing and say so; a documented gap is a contribution, a substituted guess is not.

It also argues for retiring publication-date exclusions. A bare “published after 2010” floor is rarely a methodological choice — open sources reach older trials perfectly well, and the filter biases toward recent, better-funded, more-published work, which is the same direction as publication bias stacked on top of it. Either state what the cut-off actually means or drop it.

Recover the event counts yourself — and the registry trap that looks like a shortcut

To pool a trial yourself rather than inheriting somebody else's pooled number, you need the per-arm counts: events and denominator, for each arm. The new count-recovery harness is the machinery for getting them safely — 14 checks, standard-library only, offline, no API key, no AI call. Run python count_recovery_harness.py --selftest and it puts its own checks through 11 negative controls: each trap is deliberately introduced and the check must catch it. A check that has never been shown to fail is not a check.

One finding on that page is worth reading even if you never run the tool. ClinicalTrials.gov requires an all-cause death count in the adverse-events module, so for any trial with posted results it is there as a clean integer — even when the trial's efficacy outcomes are posted only as percentages. It looks like a universal key. It answers a different question: the safety population over the adverse-event collection window, not the efficacy analysis set over the efficacy follow-up. Across six trials it was identical twice (SPRINT, DECLARE-TIMI 58), close twice, out by about 100 events per arm once (ODYSSEY OUTCOMES), and out by more than double once (EMPA-KIDNEY: 314/353 against 148/167). Nothing on the page tells you which case you are in.

And here is the part that generalises well beyond registries. The obvious defence is to check your recovered counts against the trial's published hazard ratio. For ODYSSEY OUTCOMES the wrong counts reproduce it: the adverse-events pair gives a risk ratio of 0.856, the efficacy pair 0.852, against a published 0.85. Both pass. A ratio is insensitive to anything that scales both arms together, which is exactly what swapping one population for another usually does. So the rule the harness encodes — agreement authenticates nothing; only disagreement is informative — is why that check warns on mismatch and stays silent on a match, and never passes a cell on its own. Before you rely on any consistency check, ask what it would look like if the data were wrong; if the answer is “the same”, it is decoration. Full write-up: registry extraction traps.

Six trials, chosen because they were the ones being extracted, not sampled. Treat the pattern as real and the proportions as nothing.

Screen a published review for one trial counted twice

Of six published syntheses adjudicated in depth, three were erroneous, and all three were the same species of error: one trial counted as several, or characterised as something it is not. In two of them a pooled analysis of two trials sat in the included-studies table alongside the two trials it pools, and each of those trials also appeared twice under different author names — in one case behind a one-letter misspelling of the first author's surname, which was enough to keep two rows for one trial side by side undetected. The root cause is matching on the citation string instead of on trial identity.

It leaves a cheap, computable signature: participant total inflated well past the number ever randomised for the question, together with I² near zero — which is what pooling data against itself produces, because duplicated rows agree with themselves perfectly and drive the between-study variance down. Every pooled interval comes out falsely narrow. scripts/trial-identity-screen.py takes a CSV of the included-studies table — typed out of a published paper, no access required — and looks for it:

python scripts/trial-identity-screen.py my_table.csv --universe 22000 --i2 0

It reconciles arms as well as totals (the strongest signal: in the confirmed case the pooled row's arms matched its two components exactly and independently — 2833+3686=6519 and 2841+3666=6507), matches near-duplicate arm splits under a transcription tolerance, catches transposed arm columns, and reports the I² conjunction. A worked example table ships with it, along with a clean one so you can see it stay quiet. Low heterogeneity on its own is not suspicious and the tool will not say it is — consistent trials produce it legitimately. It is the co-occurrence that is diagnostic.

A screen, not a verdict. The tolerance that catches real transcription noise will also collide two genuinely distinct trials of similar size, so every hit is a prompt to check the registry identifier. And it never looks at comparator, population, or outcome definition — the other way a review mis-characterises a trial it did find.

A claim of ours the evidence revised

We started from the position that published reviews fail on two counts: they do not search widely enough, and they do not check what they find. Six syntheses in, there are three confirmed checking failures and zero confirmed breadth failures. The most informative case cuts straight against us: the worst of the three had a broader search than several reviews that got the right answer — multiple databases, preprints, no date or language filter, and explicit translation of non-English text — and still produced a badly wrong result, because it counted the same patients three times. Searching harder would not have caught either error we found. That does not mean breadth failures do not exist; it means this sample has not caught one in the act, and the sample was chosen to find checking problems. We are publishing the row that does not flatter the original claim because the rest is only worth reading if we do.

What actually blocks access — measured, not assumed

If you work without institutional subscriptions, the usual warning is that paywalls will limit you. In one audit that logged every retrieval failure by type: of eight targets, six presented a barrier — five were our own tooling (bot-blocks, JavaScript-rendered pages, a tool silently stripping content) and one was a genuine paywall. All five tooling barriers eventually yielded; the paywall did not, after four routes. Two lessons are worth more than the rates: a failed fetch is never a data absence — record what stopped you, because “403” is a fact about your access and “not reported” is a fact about the trial — and “not found” often means “not named”: a Chinese-language trial stayed invisible to a PubMed search because its journal is not indexed in MEDLINE, while being free to read the whole time. A PubMed-only search measures indexing, not existence.

The layer that genuinely cannot be recovered is not the paywalled one — it is the unpublished one. The clean example: a trial's appendix prints thirty-five subgroup estimates and no interaction p-values anywhere, while the main text asserts the subgroups are consistent. That number is not behind a wall. It was never computed, or never reported. Open access does not touch that layer. Security model — what the SHA gate does and doesn't protect

The SHA gate is for download integrity, not source integrity. Specifically:

  • What it catches: tampering of install.ps1 / install.sh between the GitHub Pages CDN and your laptop (corrupted download, MitM injection on a hostile network). The installer hashes itself against docs/HASH.txt / docs/HASH-linux.txt fetched from the same origin and refuses to run on mismatch.
  • The bootstrap entrypoints (bootstrap.ps1, e156-setup.bat, e156-setup.sh) are not SHA-gated. They run before the gate fires; they then fetch the rest of the repo and the SHA-gated install.ps1 validates itself. So a tampered bootstrap script could short-circuit the gate entirely. The bootstrap layer is small and auditable — read the source via the links below before running it on a security-sensitive machine.
  • What it does not catch: compromise of the GitHub repo itself. A bad actor with push access to mahmood726-cyber/e156-ecosystem-starter can update install.ps1 AND docs/HASH.txt together and the gate will pass. Any curl|bash-style installer has this property.
  • For high-trust installs (e.g. a department lab with sensitive data), prefer the git-clone path with a tagged release: git clone --branch v0.x.y --depth 1, verify the tag's GPG signature, then run .\install\install.ps1 from the clone. The signed tag is a trust anchor independent of the Pages CDN.
  • What runs locally: the install touches ~/.claude, ~/.gemini, ~/.codex, and (if you opt in) %USERPROFILE%\code\. It does not require admin rights, does not modify system PATH, and rolls back on failure. The full source is auditable on GitHub.
  • Sub-installer pinning: the optional Sentinel and Overmind chains pip-install from GitHub. Both are pinned by default (SENTINEL_REF=v0.1.0, OVERMIND_REF=<known-good-SHA>) so a fresh install is reproducible even if upstream main drifts. To opt into bleeding-edge or roll back a release: set $env:SENTINEL_REF / $env:OVERMIND_REF to any branch, tag, or commit SHA before running the chain installer.
